# The anki-xml language

This document is the normative specification of the input format. If the
implementation and this document disagree, the implementation is wrong
unless this document is updated alongside the fix.

## 1. Document shape

A document is an XML file whose root element is `<anki>`. The XML
declaration `<?xml version="1.0" encoding="UTF-8"?>` is optional but
recommended.

```xml
<?xml version="1.0" encoding="UTF-8"?>
<anki deck="AI Import::Vocab">
  <note type="Basic" tags="greetings">
    <front>Hola</front>
    <back>Hello</back>
  </note>
</anki>
```

## 2. The `<anki>` root element

| attribute | type   | required | meaning                                                       |
|-----------|--------|----------|---------------------------------------------------------------|
| `deck`    | string | **no**   | default deck for every `<note>` that does not set its own     |

If `<anki>` has no `deck` and any `<note>` has no per-note `deck`,
validation fails for those notes.

The `<anki>` element may contain zero or more `<note>` children, plus
comments and whitespace.

## 3. The `<note>` element

| attribute | type   | required | meaning                                                       |
|-----------|--------|----------|---------------------------------------------------------------|
| `type`    | enum   | yes      | one of the supported note types, see §4                       |
| `deck`    | string | no       | overrides the `<anki>` default deck for this note             |
| `tags`    | string | no       | whitespace-separated tags, e.g. `"biology cells mitochondria"` |

Per-note `deck` wins over `<anki deck=...>`. If both are empty, the
note is rejected.

Children of `<note>` are field elements listed in document order.
Allowed field tags are `front`, `back`, `text`, `extra`, `addReverse`.
Duplicate field tags (e.g. two `<front>`s in the same note) are
rejected.

## 4. Supported note types and their fields

The five strings below are exact — they match Anki's internal note-type
identifiers byte for byte.

### 4.1 `Basic`

| field  | required | meaning                                            |
|--------|----------|----------------------------------------------------|
| `front`| yes      | the question; non-empty                            |
| `back` | yes      | the answer; non-empty                              |

Forbidden: `text`, `addReverse`. `extra` is not part of this model.

### 4.2 `Basic (and reversed card)`

| field  | required | meaning                                            |
|--------|----------|----------------------------------------------------|
| `front`| yes      | the question                                       |
| `back` | yes      | the answer; Anki generates the reverse automatically |

Forbidden: `text`, `addReverse`. The reverse card is generated by Anki
itself — no extra markup is needed in this file.

### 4.3 `Basic (optional reversed card)`

| field        | required | meaning                                                   |
|--------------|----------|-----------------------------------------------------------|
| `front`      | yes      | the question                                              |
| `back`       | yes      | the answer                                                |
| `addReverse` | yes      | exactly `yes` or `no` (case-insensitive, trimmed)         |
| `extra`      | no       | shown only when the reverse card is generated             |

The literal string `yes` or `no` is required — `true`, `1`, `True` are
not accepted. `extra` is permitted but only meaningful when
`addReverse` is `yes`.

### 4.4 `Basic (type in the answer)`

| field  | required | meaning                                            |
|--------|----------|----------------------------------------------------|
| `front`| yes      | the prompt shown to the user                       |
| `back` | yes      | the answer they have to type                       |

Forbidden: `text`, `addReverse`. Identical field shape to `Basic`;
Anki renders the answer differently (with a typing box).

### 4.5 `Cloze`

| field  | required | meaning                                                       |
|--------|----------|---------------------------------------------------------------|
| `text` | yes      | contains one or more `{{cN::...}}` markers                    |
| `extra`| no       | optional additional context                                   |

Forbidden: `front`, `back`, `addReverse`.

A cloze marker is `{{c1::something}}`, `{{c2::something else}}`,
etc. The digit after `c` is the cloze ordinal; Anki groups all `c1`
markers into the first cloze, all `c2` markers into the second, and so
on. At least one marker is required.

`extra` is the only field that may be empty (the validator skips the
"non-empty" check on it).

## 5. Non-empty content

A field is "non-empty" if, after stripping every `<...>` tag and then
trimming whitespace, anything remains. So `<front><br/></front>` is
empty; `<front><br/>&nbsp;</front>` is not.

This applies to every required field and to `<extra>` when present.

## 6. Tags

The `tags` attribute is a single string of whitespace-separated
tokens. Tokens are split on any run of whitespace (`\s+`). Empty
tokens are dropped. The empty string and the missing attribute both
produce `[]`.

```xml
<note type="Basic" tags="biology cells  mitochondria">
```

becomes `["biology", "cells", "mitochondria"]` (the double space is
collapsed).

## 7. Comments

XML comments `<!-- ... -->` are allowed anywhere a tag is allowed.
Comments inside field content are dropped during extraction (their
text is not included in the field).

```xml
<anki deck="X">
  <!-- this note is fine -->
  <note type="Basic" tags="x">
    <front>/* not a comment */ Q</front>
    <back>A</back>
  </note>
</anki>
```

The literal text `/* not a comment */` is preserved on the front.

## 8. The XML declaration

`<?xml version="1.0" encoding="UTF-8"?>` is allowed at the top of the
file and is treated as a processing instruction (ignored by the
parser). Other processing instructions are also ignored.

## 9. What is NOT supported in v1

- Custom note types (`MyNoteType` defined in Anki).
- `<anki>` attributes other than `deck` (e.g. `model`,
  `template`).
- Nested `<note>` elements.
- Field tags other than the five listed above; anything else inside a
  `<note>` is silently ignored.
- Media references beyond standard HTML `<img>` and `<audio>`.

These are deliberate limitations; support for them would require
either an extensible schema or explicit configuration.
